## 6. Endpoints (follow existing `/leads/:id/research` convention)

### POST `/api/leads/:id/pain` — initiation
Request: `{ "provider": "PERPLEXITY" | "GEMINI" }`
Flow: validate provider (400 `INVALID_PROVIDER`) → lead exists (`db.leads.findUnique`, 404 `RESOURCE_NOT_FOUND`) → `leadPainContextAssembler.assemble(leadId)` (throws `RESEARCH_CONTEXT_NOT_FOUND` / `QUALIFICATION_CONTEXT_NOT_FOUND` → mapped 404) → `painAnalysisService.initiateAnalysis(leadId, {companyName, industry, website, summary, evidence, gaps: []}, {summary, signals: commercialSignals}, provider, {researchVersionId, qualificationVersionId})` → `createTask` stamps the two version UUIDs on the task row.
Response 201: `{ data: { taskId, prompt, researchVersionId, qualificationVersionId, status: 'READY' } }`

### POST `/api/leads/:id/pain/result` — result submission
Request: `{ "taskId": "<uuid>", "result": "<ai text>", "evidence": [{ id, text, sourceUrl? }, ...] }` (evidence optional array).
Flow: validate taskId/result present (400 `INVALID_REQUEST`) → `manualAITaskService.getTask(taskId)`; `!task || task.leadId !== leadId` → 404; `taskType !== 'PAIN_ANALYSIS'` → 409 `PAIN_TASK_TYPE_MISMATCH`; **exact versions read from the task row** (`researchVersionId`/`qualificationVersionId` stamped at initiation — never from the body, never re-resolved); missing stamps → 409 `PAIN_TASK_VERSION_IDENTITY_MISSING` (legacy/PAIN-less tasks) → `painAnalysisService.processAnalysisResult(leadId, result, researchVersionId, qualificationVersionId, evidence, taskId)` → PainVersionManager transaction (taskId lock → re-read → guards → leadId lock → persist → task correlation → REVIEWED → COMMIT).
Response 201: `{ data: { taskId, painAnalysisId (real persisted UUID), analysisVersion, status, overallConfidence, primaryPainId, painCount, unresolvedQuestions } }`

### Error mapping (both POST endpoints)
`PAIN_ERROR_STATUS`: `PAIN_TASK_ALREADY_REVIEWED→409`, `PAIN_TASK_NOT_FOUND→404`, `PAIN_TASK_TYPE_MISMATCH→409`, `PAIN_TASK_LEAD_MISMATCH→409`, `PAIN_RESEARCH_VERSION_NOT_FOUND→404`, `PAIN_QUALIFICATION_VERSION_NOT_FOUND→404`, `RESEARCH_CONTEXT_NOT_FOUND→404`, `QUALIFICATION_CONTEXT_NOT_FOUND→404`, `LEAD_NOT_FOUND→404`, `INVALID_PROVIDER→400`, `INVALID_REQUEST→400`; unknown → 500 `INTERNAL_ERROR`. Same `{ error: { code, message } }` envelope as the rest of the project.

## 7. Task Identity / Version Flow (end-to-end)
```
initiation:  assemble(leadId) → researchVersionId (FK via research_data.research_version_id,
             Migration 036) + qualifications.id (canonical row for latest version)
             → createTask stamps manual_ai_tasks.research_version_id / qualification_version_id
result:      getTask(taskId) → versions read FROM THE TASK (identity source)
             → processAnalysisResult(..., taskId)
             → PainVersionManager: re-validates both version UUIDs exist, persists
               pain_analyses with the same IDs, updates the task
               (pain_analysis_id = real analysis UUID, same version IDs, status=REVIEWED)
             → COMMIT (atomic; replay → PAIN_TASK_ALREADY_REVIEWED → 409, no second version)
```
No timestamps, no blind "latest at result time", no fake IDs. In-transaction version validation means a deleted version between initiation and result → rollback with `PAIN_RESEARCH_VERSION_NOT_FOUND`/`PAIN_QUALIFICATION_VERSION_NOT_FOUND` (404).
