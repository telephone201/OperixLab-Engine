## 8. Pain Transaction Design (as implemented)
```
BEGIN
  [if taskId]
    advisory lock(taskId)                      ← first
    re-read manual_ai_tasks FOR UPDATE
    guards: NOT_FOUND / TYPE_MISMATCH / LEAD_MISMATCH / ALREADY_REVIEWED
    validate research_versions.id exists
    validate qualifications.id exists
  advisory lock(leadId)                        ← second
  compute analysis_version (latest+1 under lead lock)
  INSERT pain_analyses (research_version_id, qualification_version_id persisted)
  INSERT pains (per pain)
  INSERT pain_evidence (per evidence link)
  UPDATE pain_analyses.primary_pain_id
  [if taskId]
    UPDATE manual_ai_tasks:
      pain_analysis_id = analysisId (real UUID)
      research_version_id / qualification_version_id = same validated values
      status = 'REVIEWED'
  mutate analysis object with real IDs
COMMIT
```
No writes outside the transaction except console.log + auditLogger (console-only by design).

## 9. Guarantees Achieved
1. Pain persistence fails → task never becomes REVIEWED (single transaction).
2. Task update fails → Pain persistence rolls back.
3. Replay after REVIEWED → `PAIN_TASK_ALREADY_REVIEWED`, no second version (no new `pain_analyses` row, rollback before any write).
4. Concurrent same-task processing serialized by taskId advisory lock + `FOR UPDATE`.
5. Response-loss + retry → retry hits REVIEWED guard; no duplicate Pain. (Consumer recovery of the result: task.pain_analysis_id stores the real analysis id.)
6. `manual_ai_tasks.pain_analysis_id` = actual persisted `pain_analyses.id` (same variable `analysisId` used for both INSERT and UPDATE).
7. Version correlation = exact validated IDs (no timestamps, no "latest" guessing, no fake IDs).
8. Lock order is always taskId → leadId (deadlock-safe, fixed order).
